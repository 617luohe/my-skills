# 老油条 — Python 交付节奏管理

用项目现有的交付开关控制交付节奏；没有现成机制时，才使用 `branch_config.json` 默认适配器。

## 核心原则

1. **现有框架优先。** 沿用项目已有开关的文件、API、schema、命名和校验方式，不默认引入第二套配置。
2. **单一事实来源。** 每次执行只认一个交付配置来源；来源冲突时停止写盘并给出一条兼容建议。
3. **一条推荐。** 默认直接给出最优交付建议；只有用户要求调整时才展示候选。
4. **统一写入门禁。** 写盘前一次性预览交付配置、交付说明和历史记录的全部变更，确认后再写入并校验。
5. **收益必须有依据。** 优先使用测试/基准、项目文档、注释或提交记录；只有定性依据时只写定性效果，没有依据则标记“待验证”，不编造指标。
6. **甲方语言。** 交付说明描述业务效果，不暴露算法、数据结构等实现细节。
7. **保持简洁。** 默认终端输出不超过 20 行；无候选时说明“无待交付升级”并退出。
8. **不自动提交。** 不执行 git commit 或 push，除非用户明确要求。

## 首次探查与适配契约

首次调用、已选来源失效或项目结构变化时执行完整探查；同一会话后续调用复用已确认结论，写入前只验证来源仍有效。

### 探查顺序

1. 阅读 `CLAUDE.md`、`README*`、`docs/`、部署文档和配置说明。
2. 搜索 feature flag/toggle、配置中心、环境变量、settings/config、策略表、插件/实现选择器和发布清单。
3. 沿运行入口确认修改会影响真实运行行为，并排除废弃样例和测试夹具。
4. 多个候选按以下优先级选择：项目文档明确指定 > 生产代码读取 > 部署流程注入 > 其他配置。

### 统一适配契约

无论底层框架是什么，都先整理出：

- **当前状态**：模块或能力 → 当前启用状态/实现；
- **候选状态**：模块或能力 → 可选状态/实现；
- **变更方法**：应修改的文件、API、CLI 或环境变量；
- **校验方法**：原框架的 schema、测试或检查命令；
- **收益来源**：测试、基准、文档、注释或提交记录。

处理结果：

- 找到可用框架：将其作为唯一“交付配置”，按原方式读写和校验。
- 没有可用框架：使用默认适配器，细节见 [references/default-adapter.md](references/default-adapter.md)。
- 能力不足或来源冲突：停止写盘，说明缺口，只给一条兼容改造建议并等待确认。
- 用户明确要求新建、迁移或并存：展示新事实来源和回滚方案后再确认。

## 意图路由

按语义只走一条路径：

| 用户意图 | 路径 |
|---|---|
| 查看当前状态、待交付项 | 状态查看 |
| 指定某模块/能力切换 | 精确切换 |
| 询问这次交什么、快到节点、无参数调用 | 交付建议 |
| 只要求交付说明 | 说明生成 |
| 明确要求初始化，且没有可复用框架 | 初始化默认适配器 |

模糊时走“交付建议”。不要询问用户选择模式。

## 统一执行流程

所有会写盘的路径复用本流程：

1. **读取**：读取交付配置、候选状态和 `.laoyoutiao/delivery-log.json`；日志不存在时按空历史处理。
2. **计算**：找出尚未启用、相对上次快照新增或可形成下一阶段收益的候选；无候选则干净退出。
3. **推荐**：围绕一条叙事线推荐 2–4 项；有历史则在性能、功能、体验、安全之间轮转，无历史则选择候选最多的叙事线。
4. **完整预览**：一次性展示配置 diff、拟生成的交付说明路径、历史记录变化和校验方法。
5. **确认**：等待用户自然语言确认。用户要求调整时才展示相关候选并重新预览。
6. **写入**：按适配契约修改唯一交付配置，生成说明并追加历史记录。
7. **校验**：运行原框架校验；失败则报告错误和已写入内容，不宣称成功。
8. **结果**：简要列出实际变更、校验结果和交付说明路径。

## 各路径差异

### 状态查看

只读。输出模块/能力、当前状态、候选状态、叙事线、待交付数和上次交付时间，不生成文件。

### 精确切换

从自然语言解析目标，验证其存在于适配契约的候选状态中，然后进入统一流程的“完整预览”。无法解析时只说明缺少的模块名或目标状态，不默认展开全量菜单。

### 交付建议

执行完整统一流程。建议收益按以下顺序取值：

1. 测试或基准数据；
2. 项目文档、实现注释、docstring 或提交记录；
3. 可验证的定性效果；
4. `待验证`。

### 说明生成

黄金路径触发时使用本次变更；独立调用时对比当前交付配置与上次快照，最后回退到该配置的 git diff。模板见 [references/delivery-note-template.md](references/delivery-note-template.md)。独立生成说明也必须经过统一写入门禁。

### 初始化默认适配器

仅在完整探查未发现可复用框架，或用户明确要求新建默认框架时进入。先展示将创建的文件和初始状态；确认后按 [references/default-adapter.md](references/default-adapter.md) 初始化。

## 异常处理

| 场景 | 行为 |
|---|---|
| 已有框架但没有 Python 注册表 | 从框架 schema、调用点和可选值建立适配契约，不引入注册表模板 |
| 多个事实来源互相冲突 | 停止写盘，推荐保留生产代码实际读取的来源并等待确认 |
| 配置引用已删除状态/实现 | 展示修复预览，确认后按原框架修复 |
| 原框架不能表达交付节奏 | 推荐最小兼容改造，不静默创建 `branch_config.json` |
| 没有候选 | 输出“无待交付升级”并退出 |
| 校验失败 | 报告失败命令、错误摘要和实际写入内容，不生成成功结论 |

## 完成检查

- 已使用唯一且有效的交付配置来源；
- 未在无明确要求时创建第二套配置；
- 所有写入内容已统一预览并获得确认；
- 收益描述有依据且未编造指标；
- 写入后已运行原框架校验；
- 交付说明使用甲方语言。
