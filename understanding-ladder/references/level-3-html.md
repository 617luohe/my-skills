# 第 3 级：交互 HTML 页

## 什么时候用

内容的核心是「**改一个东西，看另一个东西怎么变**」：参数怎么塑造曲线、阈值怎么改变错误率、哪个选项在什么条件下胜出。

用文本，读者只能相信作者。用滑块，读者自己看到变化，还能试作者没提到的情形。

## 第 1 步：先草稿，再定参数

1. 写出解释机理的第 1 级草稿。
2. 从草稿里挑出**最重要的 1~3 个参数**。再多读者就不知道从哪下手。
3. 给每个参数写下合理的取值范围和默认值。默认值要让图处于有意思的状态。

## 第 2 步：页面版式

从上到下：

1. **一行结论**：这一页要让人看明白什么。
2. **交互区**：滑块 + 实时图。每个滑块旁边显示当前值和单位。
3. **解释**：第 1 级草稿。
4. **试一试**：2~3 条具体提示，例如「把利用率从 90% 拖到 95%，看延迟翻了几倍」。
5. **要核对什么**：模型的假设、简化了什么、哪些数字是示例。

## 第 3 步：技术要求

- **一个 HTML 文件**，CSS 和 JS 内联，不用 npm，不用构建，双击打开。
- 优先用原生 JS 加 `<canvas>` 或 `<svg>`。确实需要图表库时才从 CDN 加载（例如 Chart.js），并保证正文离线可读。
- 拖动过程中**实时**重算重绘，不要等松手。
- 手机上可用：宽度自适应，滑块够大。
- 颜色承载含义：一个量对应一种颜色，图和正文一致。
- 可选：加一个「复制当前参数」按钮，读者可以把设定发回给 agent。

## 第 4 步：交付

1. 用描述性的文件名存到工作目录，例如 `queue-latency-explainer.html`。
2. 告诉用户路径。环境允许就在浏览器里打开。
3. 在聊天里用 2~3 句说明这一页展示了什么、先动哪个滑块。

## 自检

- [ ] 不动任何滑块时这一页能看懂吗？（默认状态必须有意义）
- [ ] 每个滑块都显示值和单位吗？
- [ ] 坐标轴有名称和单位吗？
- [ ] 术语和草稿一致吗？
- [ ] 示例数据标明是示例了吗？
- [ ] 公式对吗？用手算得出的值验证一次。
