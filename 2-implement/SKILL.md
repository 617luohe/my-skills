# 2-implement — TDD 编码实现

使用 `/tdd` 技能进行红-绿-重构循环开发。

## 编码准则（贯穿全程）

沿用 CLAUDE.md「工作哲学·编码」四准则与 `/tdd` 的完整定义，此处不重复：先想后写、最小代码、外科手术、目标驱动。

## 开发流程

### 1. 理解任务

从任务清单（`docs/plans/<feature>/tasks.md`，由 `/1-plan` 产出）或 issue 中提取功能切片、验收标准、AFK/HITL 标记、前置依赖与 Write Set。`[HITL]` 任务在首个需决策或不可逆动作前暂停；所有受该决策影响的任务必须以它为依赖门。

### 1.5 条件式并行调度

执行前分别探测宿主是否提供 fresh context，以及基于同一冻结基点的隔离可写上下文和可回传变更包。仅当至少两个切片的依赖已验收、Write Set 互斥、共享接口与唯一 owner 已固定、HITL 无未决影响、运行资源可隔离，且收益高于调度成本时并行；并行能力不足时按同一 DAG 顺序 fresh context 执行，fresh context 也不可用时在主上下文顺序执行。

每个 worker 只修改其 Write Set，独立运行验收标准对应的局部验证，仅返回变更包与验证证据，不 commit、不 merge。主流程是唯一合流者，按 DAG 拓扑顺序把变更包应用到未提交工作区；**冲突即停止**：发现写集重叠、越界修改、工作区漂移、变更包无法应用或接口不兼容时，报告受影响任务，不自动解决，重新划分边界或降级为串行。全部合入后只在**最终合流态**运行完整门禁。

### 2. TDD 开发

使用 `/tdd` 技能：规划（读 CONTEXT.md/ADR，确认接口，列出要测行为）→ 示踪弹 → 递增 RED→GREEN → 重构。测试策略按行为风险判定，见 `/tdd` 的「测试策略」章节，此处不重复。

### 3. 验证

用项目原生 test/type/lint/build 命令（从任务清单、贡献文档、配置或 CI 确认，不写死工具名）在最终合流态跑完整套件；全部通过后进入自检。

### 4. 自检 + 交接

自检是轻量门禁，不是正式审查：项目配置的完整 test/type/lint/build 门禁通过；快速扫描重复与命名。自检通过后带着**未提交改动**交给 `/3-review` 正式验收，显式传递：

- **审查基点** — 相对默认分支的基点（先探测 `git symbolic-ref refs/remotes/origin/HEAD`，不写死 `main`）+ 实际 diff 范围
- **需求来源** — 任务清单路径或 issue 引用
- **diff 审查意图** — 希望 Review 重点核对的行为、风险或范围

本阶段**不执行 `git commit`**，也不自动进入 `/5-git`。

## 按评审意见修复（复评回环）

`/3-review` 裁决 FAIL 时逐条修复阻断项；PASS WITH WARNINGS 默认携带 warning 记录交接，仅用户明确选择的 warning 进入回环。回环由 `/3-review` 定义：最小修复 → 全量重验 → 携带原审查基点、需求来源、diff 范围与每条意见「已修复/未修复/拒绝+理由」交回复评；未修复或拒绝必须写明理由，不静默忽略。

## MUST 规则

1. **绝不在 RED 时重构。** 全部变绿后才检查提取重复/加深模块。
2. **测试通过公共接口验证行为，不验证实现细节。**
3. **遇 HITL 任务时暂停决策。** 展示当前进度和待决策项，等待用户输入后继续。
4. **开发完成后必须自检，再交给 `/3-review` 正式验收。** 携带审查基点与需求来源；保持改动未提交，不跳过验收、不自动调用 `/5-git`。

## 何时使用

- `/1-plan` 产出任务清单后逐个执行
- 用户明确要求"开发"、"实现"、"TDD"
- 方案已明确，直接进入编码阶段

## 与其他技能的关系

- **输入** — `/1-plan` 产出的 tasks.md / PRD.md / CONTEXT.md
- **调用** — `/tdd`（canonical `vocabulary/tdd`，核心循环）
- **输出** — 通过测试的未提交代码 + 自检结果 + 审查基点 + 需求来源 → `/3-review`
- **审查通过后** — 仅用户明确授权时 → `/5-git`

## 完成标准

- 实现已按 `/tdd` 完成红-绿-重构循环。
- 项目配置的完整 test/type/lint/build 门禁已通过。
- 改动未提交，已携带审查基点、需求来源与 diff 意图交给 `/3-review`。
