# TDD — 测试驱动开发

用项目已定义的测试框架和命令，先写失败测试，再写最少实现。

## 核心理念

测试**通过公共接口验证行为**，不验证实现细节；代码可以完全重写，测试不应该变。优先集成风格：走真实调用路径，验证用户可感知行为。好的/坏的测试判别见 `references/test-principles.md`。

## 反模式：水平切片

先写全部测试再全部实现（水平）会验证想象的行为；按一切片一切片推进（垂直）才响应上一轮教你的东西。

## 循环

1. **规划**：读 `CONTEXT.md`/ADR，确认接口，列要测的行为（不是实现步骤）；从项目清单/CI 确认原生测试命令，不按语言猜。
2. **示踪弹**：写一个测试确认一件事 → 用原生命令确认它因目标行为缺失而失败（可信 RED）→ 最少代码让它过（GREEN）。
3. **递增**：对每个剩余行为重复 RED→GREEN，一次一个，不提前写下一个、不超前实现。
4. **重构（全绿后）**：提取重复、深化浅模块、删投机代码；每次重构后原生命令仍全绿。

## 测试策略（按行为风险，而非任务规模）

- 行为变化默认新增自动化回归测试；纯文档/格式/机械生成物或已有公共接口测试覆盖时可例外，但记录验证证据。
- 无法自动测试时说明 seam 缺失与风险，不静默以手动验证替代。

## MUST 规则

1. **RED 必须可信** — 只接受因目标行为缺失而失败的红，不接受环境/语法/依赖错误造成的假红。
2. **绝不在 RED 时重构** — 全绿后才检查提取重复/加深模块。
3. **一次一个测试，最少代码通过** — 不提前实现未测试的功能。
4. **只用项目原生命令** — 未配置自动化测试时交回父工作流记录 seam 缺失与风险，不临时指定框架。

## 完成条件

- 每个行为切片有可观察的可信 RED 与对应 GREEN 证据。
- 测试只依赖公共行为，重构后项目原生测试仍全绿。
- 例外切片已记录无需新增测试或无法自动测试的证据与风险。
