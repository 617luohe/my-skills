# Test-Driven Development

TDD 是 red → green 循环。本技能是让这个循环产出值得保留的测试的参考：什么是好测试、测试放哪、反模式、以及循环的规则。每一节在每一个周期都适用：在循环之前和之中查阅它们，而非之后。

探索代码库时，读 `CONTEXT.md`（若存在），让测试名和接口词汇匹配项目的领域语言，并尊重你所触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而非实现细节。代码可以彻底改变；测试不该。好测试读起来像一份规格："user can checkout with valid cart" 精确告诉你存在什么能力，并且因为不关心内部结构而能在重构后存活。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## Seams：测试放哪

**seam** 是你测试所在的公共边界：你观察行为而不伸手进内部的接口。测试活在 seam 上，永不针对内部。

**只在预先商定的 seam 上测试。** 写任何测试之前，写下被测的 seam 并与用户确认。没有测试写在未确认的 seam 上。你没法测试所有东西，所以提前商定 seam，是让测试火力落在关键路径和复杂逻辑、而非每个边角上。

问："公共接口是什么，我们应该测哪些 seam？"

当接口本身的形状成问题时（模块有多深、seam 属于哪、接口该暴露什么），Call the Skill tool with "codebase-design" 取词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些词的共享源头，是一份可查阅的参考，不是要跑的一个 session。

## 反模式

- **实现耦合**：mock 内部协作者、测私有方法、或走旁路验证（查数据库而非用接口）。特征：你重构了但行为没变，测试却破了。
- **同义反复**：断言按代码的方式重算期望值（`expect(add(a, b)).toBe(a + b)`，手工同法推导的快照、断言自身等于自身的常量），所以按构造必过，永远无法与代码产生分歧。期望值必须来自独立的真相源：已知正确的字面量、手工算例、spec。
- **水平切片**：先写全部测试，再写全部实现。批量测试验证的是*想象中*的行为：你测的是事物的*形状*而非用户可感的行为，测试对真实变化失去敏感，而且你在理解实现之前就锁定了测试结构。改为**垂直切片**工作：一个测试 → 一个实现 → 重复，每个测试是一发**tracer bullet**，回应上一个循环教你的东西。

## 循环的规则

- **先红后绿。** 先写失败测试，再写恰好让它通过的代码。不预想未来的测试，不加投机功能。
- **一次一片。** 每循环一个 seam、一个测试、一个最小实现。
- **重构不属于循环。** 它属于 review 阶段（见 `code-review` 技能），而非 red → green 实现循环。
