# UI Prototype

在**单一路由**上生成**几个结构迥异的 UI 变体**，用底部浮动条切换。用户在浏览器里翻变体，选一个（或从每个里偷点东西），其余扔掉。

若问题关于逻辑/状态而非长相，选错分支了，用 LOGIC.md。

## 何时是对的形态

- "这页面应该长什么样？"
- "提交 dashboard 前我想看几个选项。"
- "设置页试试不同布局。"
- 任何用户本会在脑袋里三个模糊 mockup 间纠结一天的时刻。

## 两种子形态：强偏好子形态 A

UI 原型在**贴着应用其余部分**时好判断：真 header、真 sidebar、真数据、真密度。孤零零的 throwaway 路由是真空，每个变体孤立看都顺眼。有合理宿主页就默认子形态 A；只有原型真的无处安放时才用子形态 B。

### 子形态 A：挂到现有页面（优先）

路由已存在。变体在**同一路由**上渲染，用 `?variant=` URL search param 门控。既有数据获取、参数、鉴权全留，只换渲染。这是默认，除非有具体理由不选。

若原型对象还没有页面、但自然会住在某页里（dashboard 新块、设置页新卡、现有流程新步骤），仍是子形态 A：把变体挂进宿主页。

### 子形态 B：新页面（最后手段）

只有被原型对象确实没有可挂的现有页面时用（如全新顶层界面、或无法合理嵌入的流程）。

建**throwaway 路由**，遵守项目已有路由约定，不自造顶层结构。命名让其一眼是原型（如路径或文件名含 `prototype`）。同样用 `?variant=` 模式。

选子形态 B 前 sanity-check：真的没有可嵌入的现有页面吗？空路由会藏住填充页才会暴露的设计问题。

两种子形态的底部浮动条一致。

## 过程

### 1. 写下问题并定 N

默认 **3 个变体**；超过 5 就不再"结构迥异"而变成噪音，封顶 5。

计划写一行，放在原型位置或文件顶注释：

> "设置页三个变体，经 `?variant=` 切换，挂在现有的设置路由上。"

用户在不在都成立。

### 2. 生成结构迥异的变体

起草每个变体，每个都要求：

- 页面目的与其可用的数据。
- 项目组件库/样式系统（TailwindCSS、shadcn、MUI、plain CSS，是什么用什么）。
- 清晰导出的组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**：不同布局、不同信息层级、不同主 affordance，不只是不同颜色。三个微调过的卡片网格不是 UI 原型，是壁纸。两个草稿太像，就带"禁用卡片网格"的明确指引重做其一。

### 3. 接起来

在路由上建单个 switcher 组件：

```tsx
// 伪代码，适配项目框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：所有既有数据获取留在 switcher 之上，每变体只换渲染子树。

子形态 B（新页面）：`/prototype/<name>` 下的 throwaway 路由挂同一个 switcher。

### 4. 建浮动 switcher

屏幕底部居中一个小的 fixed 定位条，三块：

- **左箭头**：切到上一变体（循环）。
- **变体标签**：当前变体 key，变体有导出名也带上。如 `B (Sidebar layout)`。
- **右箭头**：切到下一变体（循环）。

行为：

- 点击箭头更新 URL search param（用框架 router，如 Next 的 `router.replace`、React Router 的 `navigate`），让变体可分享、刷新后稳定。
- 键盘：`←` `→` 也切换。`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截方向键。
- 视觉与页面明显区分（如高对比 pill、微阴影），一看就不是被评估的设计的一部分。
- 生产构建隐藏：`process.env.NODE_ENV !== 'production'` 或等价检查门控，防止原型误合入把条送上生产。

switcher 放单个共享组件供两种子形态复用，位置跟随项目共享 UI 所在。

### 5. 交出去

报出 URL（和 `?variant=` 的 key）。用户随时翻；有趣的反馈通常是**"我要 B 的 header + C 的 sidebar"**——那才是他们真正想要的设计。

### 6. 捕获答案并清理

变体胜出后，捕获答案（哪个变体、为什么），再按 SKILL 描述的方式捕获原型。胜者折入真实代码，其余移去 throwaway 分支而非 main：

- **子形态 A**：胜者折入现有页面；落选变体与 switcher 从 main 去掉。
- **子形态 B**：胜出变体升级为真实路由；throwaway 路由与 switcher 从 main 去掉。

完整变体集是 primary source，落去 throwaway 分支而非垃圾桶——留在 main 的变体组件和 switcher 腐烂快、迷惑下一位读者。

## 反模式

- **变体只在颜色或文案上不同。** 那是微调不是原型。真变体在结构上分歧。
- **变体间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 毁掉要点。每个变体应可自由丢弃布局。
- **变体接真实 mutation。** 只读原型即可。变体需要 mutation 时指向 stub：问题是"该长什么样"，不是"后端能不能跑"。
- **把原型直接提升进生产。** 变体代码在原型约束下写成（无测试、最小错误处理）。折入时正经重写。
