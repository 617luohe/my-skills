# Logic Prototype

单个自包含 HTML 文件（**可分享 demo**），任何人点按钮就能驱动一个状态模型。当问题关乎**业务逻辑、状态迁移或数据形状**时用这个分支：纸面上看着合理、只有推过真实 case 才觉得不对的东西。

一个文件无需安装，可以交给非开发者（设计师、PM、领域专家）亲手感受模型。所以它说他们的语言，不说代码的。

## 何时是对的形态

- "我不确定这个状态机是否覆盖 X 再 Y 的边界情况。"
- "这个数据模型真的能表达……的情况吗？"
- "我想在写代码前感受一下 API 应该长什么样。"
- 任何想"按按钮看状态变化"的场景。

若问题是"这应该长什么样"，选错分支了，用 UI.md。

## 过程

### 1. 写下问题

写代码前先写下要原型的状态模型和问题。一段话，放在 demo 顶部可见的 intro（不只是注释）。回答错问题的逻辑原型是纯浪费，所以把问题显式化，便于之后核对——用户在看还是 AFK 都一样。

### 2. 把逻辑隔离进可移植模块

把实际逻辑（回答问题的那部分）放进单个 `<script>` 块，写成小而纯的模块，之后能整体提出并落入真实代码库。它周围的页面是 throwaway，这个模块不是。

按问题选形态：

- **纯 reducer**：`(state, action) => state`。动作为离散事件、状态为单值时好。
- **状态机**：显式状态与迁移。"现在哪些动作合法"也是问题一部分时好。
- **对纯数据类型的一组纯函数**：没有隐式当前状态、只是转换时好。
- **类/模块**：逻辑确实持有长期内部状态时，用清晰的方法面。

选最贴合问题的形态，不是最好接线到页面的那个。保持纯：不碰 DOM、`document`、按钮 handler 伸进去。页面调用它，绝不能反方向流。这让原型活过自身寿命：问题答完后，验证过的 reducer/机器/函数组自己就能提升进真实模块。

### 3. 建可分享 HTML

一个文件、纯 HTML/CSS/JS：无框架、无打包、无服务器，全内联，双击即开、邮件可发。为所有能打开它的人而写。

为非开发者写。每个标签用**领域语言**，不是代码：按钮和状态读起来像业务，不像 reducer。用大白话解释正在发生什么。

自上而下干净分层：

1. **标题 + 一句话说明**这个 demo 让你探索什么（第 1 步的问题）。
2. **当前状态**：完整相关状态，渲染为可读面板（带标签字段，非 raw JSON dump），每次点击后重渲染让变化可见。对非开发者有用的地方，点出刚刚变的是什么。
3. **自由点击按钮**：每个动作一个按钮，永远可用，让人任意顺序戳模型。每次点击派发动作并重渲染状态。
4. **引导走查**：一组**场景**，每场景一个 tab。每个 tab 放该场景的短白话描述（它setup的情境与要观察什么），下面是该场景的**有序按钮**。每一步是真实按钮：点击执行动作并前进到下一步。开始走查时重置到已知初始状态，保证场景每次都一样运行。

选那些纸面难推演的别扭 case：happy path、棘手的边界、一次"本应非法"的尝试。

美观但克制：干净排版、宽松间距、一个强调色。无动画、无花活：不与状态和按钮抢戏。

### 4. 交出去

把文件发给对方或当面打开。他们会点击走查、随时自由点击；有趣的时刻是他们说"等等，那不该行"或"咦，我以为 X 会不一样"——那些是*想法*里的 bug，正是重点。他们想要新动作或新场景就加。原型会演化。

### 5. 捕获答案与原型

原型答完问题后，先捕获答案，再按 SKILL 描述的方式捕获原型。logic 专属映射：验证过的 reducer/机器/函数组提升进真实模块（决策被吸收）；HTML 壳随行去 throwaway 分支，保持原型为 primary source，且作为单个自包含文件在那里仍可随时复跑。

## 反模式

- **别加测试。** 需要测试的原型不再是原型。
- **别接真实数据库。** 用内存状态，除非问题专门关于持久化。
- **别泛化。** 没有"以后想支持 X 怎么办"。原型只答一个问题。
- **别把逻辑和页面糊在一起。** 纯模块引用 DOM、`document`、按钮 handler，就不再可提升。页面是纯模块上的薄壳。
- **别上框架、打包器或服务器。** 一个双击即开的文件；React 应用或 dev server 毁掉"可分享"。
- **别把 HTML 壳送进生产。** 页面为手点而优化；背后的逻辑模块才值得留。
