# Prototype

原型是**回答一个问题的 throwaway code**。问题决定形状。

## 选一个分支

判断正在回答哪个问题，依据用户提示、周边代码，或用户在附近时直接问：

- **"这个逻辑 / 状态模型对路吗？"** → [LOGIC.md](LOGIC.md)。建单个可分享 HTML 文件（自由点击按钮 + 分页引导走查），把状态机推过纸面难以推演的 case，非开发者也能驱动。
- **"这应该长什么样？"** → [UI.md](UI.md)。在单一路由上生成几个结构迥异的 UI 变体，经 URL search param 和底部浮动条切换。

两分支产出截然不同的产物，所以分错就整盘浪费。问题确实含糊、用户又不在时，默认取更贴近周边代码的分支（后端模块 → logic；页面或组件 → UI），并在原型顶部声明这个假设。

## 两条分支都适用的规则

1. **从第一天起就是 throwaway，并明确标注。** 把原型代码放在离它实际将被使用处近的地方（它要prototype的模块或页面旁），让上下文显而易见，但命名让随便一瞥的读者看得出它是原型而非生产。对 throwaway UI 路由，遵守项目已有的路由约定；不自造新的顶层结构。
2. **跑起来零门槛。** UI 原型从项目 task runner 一条命令起步：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是双击即开的单个 HTML 文件。无论哪种，开跑无需思考。
3. **默认不持久化。** 状态在内存。持久化正是原型要*检验*的东西，不是它该依赖的东西。问题明确涉及数据库时，用一个带清晰 "PROTOTYPE, wipe me" 命名的 scratch DB 或本地文件。
4. **跳过打磨。** 不写测试、不加超出让原型*可跑*的错误处理、不做抽象。目的是快速学到东西。
5. **呈现状态。** 每次动作（逻辑）或每次切换变体（UI）后，打印或渲染完整相关状态，让用户看见变化。
6. **结束时捕获。** 把验证过的决策折入真实代码，然后把原型本身捕获为 **primary source**：提交到 main 之外的 throwaway 分支，并在实现 issue 上留指向该分支的 context 指针。答案（verdict 与它settle的问题）也捕获进 issue 或 commit。main 分支只留验证过的决策。
