# Diagnostic Tooling

在阶段 4 根据项目语言、已有依赖、生产权限和待验证的假设选择工具。工具输出是证据的一部分，不替代对触发条件与现象的解释。

## 选择原则

| 需要回答的问题 | 优先信号或工具 |
| --- | --- |
| 哪个输入或请求失败 | 现有测试、脱敏样本、结构化错误日志、trace |
| 状态何时变化 | 断点、限速结构化日志、trace span |
| 时间花在哪里 | 项目 benchmark、profile、trace |
| 内存为何增长 | 运行时内存快照、分配/保留分析 |
| 是否存在数据竞争 | 语言的已启用竞态检测器、受控并发试验 |

优先使用仓库已有脚本、测试、监控和已安装工具。先阅读其文档或 `--help`，确认参数、权限和数据处理要求；不编造命令、不为单次调查安装生产依赖。

## 常见能力

- Python：`breakpoint()`、`logging`、`cProfile`、`tracemalloc` 都是标准库或语言内建能力；覆盖率、重复运行和并发执行依赖项目实际安装的测试插件。
- JavaScript/TypeScript：调试器、结构化日志、Node/浏览器 profiler；具体命令取决于项目运行方式。
- Go：标准测试、`pprof` 和 race detector 是否适用取决于包、构建标签和 CI 配置。
- C/C++ 与 Rust：调试器和 sanitizer/profiler 取决于编译选项、平台和工具链。

## 证据记录

每次工具运行记录：要验证的假设、命令或操作、版本/环境、输入与时间窗、关键输出、结论和下一步。插桩必须可移除、避免秘密与个人数据，并在阶段 6 清理。
