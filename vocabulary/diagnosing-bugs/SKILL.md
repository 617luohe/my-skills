# Diagnosing Bugs — Bug 诊断循环

用于难复现的 bug、回归和性能下降。每一步都保留可检查的完成条件；不能稳定复现不妨碍调查，但修复必须用同一信号验收。

## 脱敏（Redact）

本技能会让你展示命令、输出和捕获物。**先脱敏再展示**——密钥一律写 `<REDACTED>`。循环脚本对着环境变量构建，让凭据留在环境变量里，而不是出现在你展示的内容中。捕获的请求样本带鉴权头：只引用携带信号的几行。

脱敏后的输出不足以诊断时，明说并请用户提供进一步信息。

## 六阶段核心流程

### 1. 构建反馈回路
先建立**可比较的观测信号**，记录来源、时间窗、环境、筛选条件和样本量。信号可为失败测试、错误日志、trace、metrics、安全采样、请求样本、profile、内存快照；可关联请求上下文，且必须对现象敏感并生产安全。稳定或统计可信的复现用于修复验收，不是进入调查的前置条件。

- 稳定 Bug：写最小失败测试。
- 低频故障：收集请求 ID 关联的 trace、错误率或延迟；受控安全采样。
- 性能回归：记录可比较的 benchmark、profile 或内存基线。

**完成条件**：能以相同条件比较调查或修复前后的信号；稳定或统计可信复现留作修复验收。

性能基线、profile 的解读及 CPU/延迟调查步骤，遇到**性能回归**时读 [performance.md](references/performance.md)，用来选择基线和定位瓶颈。

### 2. 复现与最小化
缩小触发条件：去掉无关步骤、简化输入、隔离模块，得到最小输入和最短路径。低频故障则记录失败率、样本量、环境与已捕获异常模式，供修复后比较。

**完成条件**：最小路径仍复现，或统计样本足以与阶段 1 基线比较。

涉及**偶发、时序或并发**问题时读 [intermittent-failures.md](references/intermittent-failures.md)，用来设计重复试验、采样和竞态调查，而非把“必现”当作门槛。

### 3. 假设
根据最小路径列出 3–5 个具体、可证伪的根因假设；优先检查最近改动、高复杂度模块和历史问题区。非确定性问题还考虑时序、共享状态、环境差异和资源竞争。

**完成条件**：至少有 3 条具体假设，每条都说明可验证的预测；不是笼统地猜“某处有问题”。

### 4. 工具验证
逐个验证假设，用断点、日志插桩、trace、测试、profile 或内存快照形成**根因证据**；排除的假设也要记录结果。证据不足时回到阶段 3 增补假设。

**完成条件**：证据同时解释现象和触发条件，并能排除合理替代解释；否则不得修复。

需要按语言、运行环境或故障类型选择真实已有工具时读 [tooling.md](references/tooling.md)，用来选择工具与解释输出；只运行项目已安装或团队已批准的命令。

### 5. 修复与验收
只修复已证实的根因，不顺手重构。每次实验或改动**一次只改一个变量**，并以阶段 1 的同一信号比较。为根因新增回归测试；若无法自动测试，记录缺失的 seam、已执行验证及残余风险。

**完成条件**：回归测试和原有测试套件通过；阶段 1 信号恢复，或低频故障在预先定义的样本量、时间窗和阈值内达到统计可信改善。

内存增长、泄漏或资源保留问题读 [memory.md](references/memory.md)，用来建立快照基线、比较保留对象并验收修复。

### 6. 清理
删除 `breakpoint()`、`print()`、临时日志、临时测试和采样开关；移除临时 profile、快照或调试标签，并确认正式监控不含仅为本次调查添加的噪声。

**完成条件**：代码库无临时调试代码或文件，回归测试保留且通过，调查记录包含根因证据、验收信号和残余风险（如有）。

## 必守门禁

1. 没有可比较的观测信号，不进入假设。
2. 没有根因证据，不实施修复。
3. 一次只改一个变量，并使用同一信号比较。
4. 修复必须有回归测试或明确记录无法自动化的原因与风险。
5. 验收后必须清理所有临时调试产物。
6. 展示的命令、输出与捕获物先脱敏；密钥写 `<REDACTED>`，凭据留在环境变量。

## 何时使用

- Bug 难复现、偶发或并发相关。
- 之前正常、现在失败的回归。
- 延迟、吞吐、CPU 或内存突然恶化。
- 多次尝试修复仍未解决的问题。
