# Diagnosing Bugs

难 bug 的纪律。只有明确证明时才跳过阶段。

探索代码库时读 `CONTEXT.md`（如存在）以获得相关模块的清晰心智模型，并检查你所触及区域的 ADR。

## Redact

本技能会让你展示命令、输出和捕获物。**先脱敏每个 secret**：原位写 `<REDACTED>`。绕着环境变量建回路，让凭据留在环境里而非你展示的内容中。捕获物带 auth header：只引用携带信号的那几行。

脱敏后的输出不足以诊断 bug 时，明说并问用户。

## 阶段 1：构建反馈回路

**这就是本技能。** 其余都是机械。若你对 bug 有**紧**的 pass/fail 信号（在这个 bug 上变红），就能找到原因；bisection、假设检验和插桩都只是消费它。若没有，盯多久代码都救不了你。

在此投入不成比例的努力。**要激进。要创造。拒绝放弃。**

### 构建方式，大致按这个顺序

1. **失败测试**，在够到 bug 的 seam 上：unit、integration、e2e。
2. **Curl / HTTP 脚本**，对着开着的 dev server。
3. **CLI 调用**，喂 fixture 输入，stdout 对已知正确快照 diff。
4. **Headless 浏览器脚本**（Playwright / Puppeteer）驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace。** 真实网络请求 / payload / 事件日志存盘；隔离重放进代码路径。
6. **一次性 harness。** 起系统最小子集（单服务、mock 依赖），单函数调用即走通 bug 代码路径。
7. **Property / fuzz 回路。** bug 是"有时输出错"，就跑 1000 个随机输入找失败模式。
8. **Bisection harness。** bug 出现在两个已知态（commit、数据集、版本）之间，自动化 "在态 X 启动、检查、重复"，接进 `git bisect run`。
9. **Differential loop。** 同一输入过旧版 vs 新版（或两配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。若必须人点，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让回路仍是结构化的。捕获输出回流给你。

建对反馈回路，bug 就修好 90%。

### 收紧回路

把回路当产品。一旦有了*一个*回路，**收紧**它：

- 能更快吗？（缓存 setup、跳过无关 init、缩测试范围。）
- 信号能更锐吗？（断言具体症状，而非"没崩"。）
- 能更确定吗？（钉死时间、seed RNG、隔离文件系统、冻结网络。）

30 秒的抖动回路比没有强不了多少；2 秒的确定性回路是紧的，调试超能力。

### 非确定 bug

目标不是干净复现而是**更高复现率**。触发器跑 100×、并行化、加压力、缩时序窗、注入 sleep。50% 抖动的 bug 可调；1% 不行——持续抬到可调为止。

### 确实建不出回路时

停下并明说。列出试过什么。向用户要：(a) 能复现它的环境的访问权，(b) 脱敏捕获物（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。回路没建成就**不要**进假设。

### 完成判据：一个会变红的紧回路

阶段 1 完成 = 回路**紧**且**能红**：你能说出**一条命令**（脚本路径、测试调用、curl），**至少已经跑过一次**（展示调用与输出，脱敏），并且是：

- [ ] **能红**：驱动真 bug 代码路径、断言**用户的确切症状**，能在本 bug 上变红、修好后变绿。不是"跑完没报错"；它必须能*抓住这个具体 bug*。
- [ ] **确定**：每次同结论（抖动 bug：按上文，钉死的高复现率）。
- [ ] **快**：秒，不是分钟。
- [ ] **agent 可跑**：无人值守可跑；人只在 via `scripts/hitl-loop.template.sh` 时入环。

若你发现自己在有这条命令前读代码建理论，**停：直冲假设正是本技能要防的那个失败。** 没有能红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看它随 bug 出现而红。

确认：

- [ ] 回路产生**用户**描述的失败模式，而非恰好邻近的别的失败。错 bug = 错修复。
- [ ] 失败可跨多次运行复现（或非确定 bug，复现率高到可据此调试）。
- [ ] 已捕获确切症状（错误消息、错输出、慢计时），供后续阶段核对修复是否真解决。

### 最小化

变红后，把复现缩到**仍红的最小场景**。一次一刀地砍输入、调用方、配置、数据、步骤，每刀后重跑回路，只留对失败承重的东西。

为什么费这个劲：最小复现缩小阶段 3 的假设空间（可怀疑的活动件更少），并成为阶段 5 的干净回归测试。

完成 = **每个剩元素都承重**：去掉任何一个都让回路变绿。

复现**且**最小化之前不前进。

## 阶段 3：假设

测任何一条前，生成 **3–5 条排序假设**。单假设会锚定在第一个看似合理的想法上。

每条假设必须**可证伪**：说出它做出的预测。

> 格式："若 <X> 是原因，则 <改 Y> 会让 bug 消失 / <改 Z> 会变严重。"

说不出预测，假设就是错觉：丢弃或锐化。

**排序列表先给用户看再测。** 他们常有立刻重排的领域知识（"我们刚部署了 #3 的改动"），或知道已排除的假设。便宜的检查点，省大时间。不要阻塞：用户 AFK 就按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的具体预测。**一次只改一个变量。**

工具偏好：

1. **Debugger / REPL 检查**，环境支持就上。一个断点胜过十行日志。
2. **定向日志**，打在区分假设的边界上。
3. 绝不"全量打日志再 grep"。

**给每个 debug 日志加唯一前缀标签**，如 `[DEBUG-a4f2]`。收尾清理一次 grep 搞定。无标签日志活下来；有标签的死掉。

**性能分支。** 性能回归通常别用日志。改为：先建基线测量（时序 harness、`performance.now()`、profiler、query plan），再 bisect。先量后修。

## 阶段 5：修复 + 回归测试

**修复前**写回归测试，但只在有**正确 seam** 时。

正确 seam = 测试在调用点复现**真 bug 模式**。唯一可用 seam 太浅（bug 需要多个调用方的单调用方测试、复现不了触发链的 unit 测试）时，那里的回归测试给假信心。

**没有正确 seam 存在，这本身就是发现。** 记下来。代码架构正阻止 bug 被锁死。flag 给下一阶段。

有正确 seam 时：

1. 最小化复现转成该 seam 的失败测试。
2. 看它失败。
3. 上修复。
4. 看它通过。
5. 对原始（未最小化）场景重跑阶段 1 回路。

## 阶段 6：清理

宣布完成前必做：

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或 seam 缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删（或移到明确标注的 debug 位置）
- [ ] 证明正确的假设写进 commit / PR message，下一位调试者受益
