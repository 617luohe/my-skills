# ADR Format

ADR 放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性创建 `docs/adr/` 目录：只有首个 ADR 需要时才建。

## 模板

```md
# {决策的短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这些。一条 ADR 可以只有一个段落。价值在于记录*下*某个决定被做出、以及*为什么*，不在于填满各个 section。

## 可选 section

只有在它们带来真实价值时才加。多数 ADR 不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策被重新审视时有用
- **Considered Options**：只有被否决的备选值得记住时
- **Consequences**：只有非显然的下游影响需要点名时才加

## 编号

扫描 `docs/adr/` 找到现存最大编号，加一。

## 何时提议一条 ADR

以下三项必须全部成立：

1. **难逆转**：日后改变主意的成本是有意义的
2. **缺上下文会令人意外**：未来读者会看着代码疑惑"他们究竟为什么这样做？"
3. **真实取舍的结果**：当时存在真实的备选，你为具体理由选了其一

若决策容易逆转就跳过：你反正会逆转它。若它不令人意外，没人会疑惑为什么。若当时没有真实备选，除了"我们做了显然的事"之外没什么可记录的。

### 什么算合格

- **架构形状。** "我们用 monorepo。" "写模型是 event-sourced 的，读模型投影进 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过 domain events 通信，而非同步 HTTP。"
- **带锁定效应的技术选型。** 数据库、消息总线、鉴权提供方、部署目标。不是每个库：只有那些换掉要花一个季度的。
- **边界与范围决策。** "Customer 数据归 Customer 上下文所有；其他上下文只用 ID 引用它。" 明确的"不做"和"做"一样有价值。
- **对显然路径的有意偏离。** "我们用手写 SQL 而非 ORM，因为 X。" 任何理性的读者会假定相反方向的事。这些能阻止下一位工程师去"修复"一个刻意的决定。
- **代码里不可见的约束。** "因为合规要求，我们不能用 AWS。" "因为合作方 API 契约，响应时间必须低于 200ms。"
- **被否决的备选（当否决非显然时）。** 若你考虑过 GraphQL、因微妙理由选了 REST，就记下来；否则六个月后又会有人提议 GraphQL。
