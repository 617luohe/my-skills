# ADR Format Reference

## Standard Template

```markdown
### ADR-XXX: [简短标题，动词开头]

**日期**：YYYY-MM-DD  
**状态**：已采纳 | 已废弃 | 待定 | 已替代  
**替代者**：[如果已废弃，指向新的 ADR]

**问题**  
[需要解决什么问题？当前痛点是什么？]

**决策**  
[选择了什么方案？用一句话总结]

**理由**  
[为什么选这个方案？]
- 理由 1
- 理由 2

**后果**  
[接受什么权衡？有什么限制？]
- 好处：...
- 代价：...

**备选方案**（可选）  
- 方案 A：[为什么不选]
- 方案 B：[为什么不选]
```

## Real Examples

### Example 1: Technology Choice

```markdown
### ADR-001: 使用 FastAPI 作为 Web 框架

**日期**：2026-07-15  
**状态**：已采纳

**问题**  
需要选择 Python Web 框架构建 RESTful API，要求性能好、类型安全、文档自动生成。

**决策**  
使用 FastAPI 替代 Flask。

**理由**  
- 原生支持 async/await，性能接近 Node.js
- Pydantic 自动校验请求，类型安全
- 自动生成 OpenAPI 文档

**后果**  
- 好处：开发效率高，运行时错误少
- 代价：团队需要学习异步编程范式，社区生态不如 Flask 成熟
```

### Example 2: Architecture Decision

```markdown
### ADR-002: 采用六边形架构分层

**日期**：2026-07-16  
**状态**：已采纳

**问题**  
代码逻辑耦合严重，业务规则散落在 API 路由和数据库查询中，难以测试。

**决策**  
按六边形架构（Hexagonal Architecture）分为三层：
- `domain/`：纯业务逻辑，无外部依赖
- `adapters/`：API、数据库、消息队列适配器
- `infrastructure/`：框架胶水、配置加载

**理由**  
- 业务逻辑可独立单元测试（无需数据库/HTTP mock）
- 更换 ORM 或 Web 框架只需修改 adapters 层
- 强制依赖方向：adapters → domain（不反向依赖）

**后果**  
- 好处：可测试性强，技术债务减少
- 代价：初期需要写更多接口定义，小功能感觉过度设计
```

## Writing Guidelines

1. **标题动词开头**：使用、采用、废弃、迁移到...
2. **状态机**：
   - `待定` → 讨论中，未最终决定
   - `已采纳` → 当前生效的决策
   - `已废弃` → 不再使用，必须填 `替代者` 字段
   - `已替代` → 被更好方案取代但仍有参考价值
3. **理由要具体**：不是"性能好"，而是"QPS 从 500 提升到 2000"
4. **后果要诚实**：承认代价，不粉饰
5. **编号递增**：ADR-001, ADR-002...，按时间顺序，不跳号

## Anti-patterns

❌ 把实现细节当决策（"使用 `@lru_cache` 装饰器"不是 ADR）  
❌ 记录显而易见的选择（"使用 Git 做版本控制"）  
❌ 决策后不更新状态（方案已替换但 ADR 仍标记`已采纳`）  
❌ 没写理由直接下结论（"决策：用 PostgreSQL。理由：略。"）
