# 0-询问luohe — 技能路由器

一条**流程**是一条穿过技能的路径。大部分工作沿着**主流程**走。

## 主流程：想法 → 交付

1. **`/1-规划`** — 方案追问 → 领域建模 → 接口设计 → PRD → 任务拆解
   - 有代码库时从这里开始（维护 glossary-only 的 CONTEXT.md；ADR 单独写入 `docs/adr/`）
   - 默认批量询问（frontier 中独立决策集中问）
   - 用户说"逐步"/"一步一步"时切换为一次一问

2. **分支 — 状态机、算法或 UI 假设不确定？**
   - **是** → `/1-规划` 建立 `docs/prototypes/<topic>/` 的 throwaway prototype（单文件、可运行）验证任务；结论回写 `docs/plans/<topic>/`，原型提交 `prototype/<topic>` 分支留作证据，主分支只留决策
   - **否** → 继续任务拆解

3. **分支 — 多会话构建？**
   - **是** → `/1-规划` 产出任务清单 → 清空上下文 → 每个任务用 `/2-开发`
   - **否** → 同一上下文直接 `/2-开发`

4. **`/2-开发`** — TDD 红-绿-重构循环 → 自检（测试+类型+linter）→ 携带审查基点、需求来源和 diff 审查意图交给 `/3-检查` 正式验收（保持未提交）

5. **`/3-检查`** — 基于输入契约强制 Review，输出 PASS/PASS WITH WARNINGS/FAIL 正式交接产物

6. **`/5-版本管理`** — Review 通过后，仅在用户明确授权时 commit + push（可选）

### 并行加速（实验性）

- **`/multi-worker`** — 需要完整设计文档 + 独立子任务 + Agent配置验证

## 上游（汇入主流程）

- **陌生代码库 / 看不懂代码** → 先进行一次性只读调查，输出 `docs/analysis/<topic>.md`（项目地图、已验证事实、未知项与停止条件）；调查完成即停止。根据结果：需要决策或实施方案 → `/1-规划`，可按现有输入做验收或架构评估 → `/3-检查`，需要定位根因或修复 → `/4-调试`。不新增 skill。
- **难搞的 bug** → **`/4-调试`** 建立可比较观测信号 → 复现 → 假设 → 工具验证 → 修复 + 回归测试
- **代码腐烂 / 模块臃肿** → `/3-检查`，明确输入意图为“架构评估”；先评估架构与测试 seam，输出 `docs/analysis/<topic>.md` 和可追踪的 `docs/plans/<topic>/` 改造任务。评估完成即停止，由用户决定是否进入 `/1-规划`。

## 按规模分级（对应 CLAUDE.md 路由表）

> **唯一事实源**：本文件是路由的唯一编辑处；CLAUDE.md 的「工作流路由」速查表为本文件的常驻镜像。改路由只改本文件，再同步 CLAUDE.md 速查。

先判规模，再选路径：

| 规模          | 判定                               | 路径                                                                         |
| ------------- | ---------------------------------- | ---------------------------------------------------------------------------- |
| **S 微改动**  | 单文件、<10 行、无歧义             | 直接改 → `/5-版本管理`                                                       |
| **M 小任务**  | 单模块、方案明确；文档/配置/一次性 | 直接做 → `/5-版本管理`（文档类不强制 TDD）                                   |
| **L 中功能**  | 多文件、方案已定                   | `/2-开发` → `/3-检查` → `/5-版本管理`                                        |
| **XL 大功能** | 多模块、方案不定、需设计           | `/1-规划` → **授权** → `/2-开发` → `/3-检查` → `/5-版本管理` → `/6-最后整理` |

## 上下文管理原则

### 何时清空上下文

- **主流程 1→2→3 保持一个上下文** — grilling、spec、任务清单都在同一窗口，共享理解
- **每个 `/2-开发` 开始前清空** — 从任务清单的单个 issue 出发，不带 grilling 的详细讨论

### 何时用 `/6-最后整理`

- 完成一个阶段（如 `/1-规划` 完成、多个 `/2-开发` 全部完成）
- 结束一天工作
- 把项目交给别人

### 何时用 `/0--neat-freak`

- `/6-最后整理` 完成后，如果发现文档和代码不一致
- 定期维护（如每周一次）
- CLAUDE.md 或 memory 明显膨胀时
